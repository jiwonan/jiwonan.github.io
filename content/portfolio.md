### RDS 장애 분석 및 인프라 모니터링 체계 구축

RDS Read Replica 장애를 분석하고, 재발 방지를 위한 모니터링 시스템 구축

**[ 문제 상황 ]**
- RDS Read Replica 스토리지가 갑자기 고갈되어 서비스 장애 발생
- 장애 발생 시점에 명확한 원인을 파악할 수 없었음

**[ 조사 및 분석 ]**
- CloudWatch 로그와 RDS 지표 분석 수행
- 2달 전부터 종료되지 않은 Long Transaction 발견
- History List Length가 지속적으로 증가하고 있었음을 확인

**[ 근본 원인 ]**
- MySQL의 Repeatable Read 격리 수준에서 Long Transaction이 열려있으면 Undo Log가 삭제되지 않음
- Purge Thread가 Undo Log를 정리하지 못해 스토리지가 계속 증가
- 분석용 쿼리를 운영 DB에서 직접 실행하던 것이 원인

**[ 해결 및 재발 방지 ]**
- 분석용 DB 계정을 분리하여 운영 DB 직접 접근 차단
- Terraform으로 RDS 주요 지표(Storage, History List Length 등) Slack Alert 시스템 구축
- 장애 대응 문서화 및 팀 내 공유

**[ 성과 및 성장 ]**
- 장애 복구 및 재발 방지 체계 구축
- RDS 내부 동작 원리(Undo Log, Purge Thread, MVCC) 학습
- 인프라 모니터링의 중요성 체득

**Tech**: AWS RDS, CloudWatch, Terraform, Slack API

### 라이더 정산 로직 최적화

라이더 정산 Legacy 로직이 운영상 문제가 되어 이를 최적화

**[ 문제 상황 ]**
- Scheduler를 이용해 매일 생성하던 정산 데이터가 백엔드 배포로 인해 미작동
- 운영 시간에 정산 API를 실행, API 중복 실행으로 인한 주요 table row lock 발생
- lock 해결을 위한 DB 재부팅으로 관련 없는 고객 앱에도 영향

**[ 역할 ]**
- 계산, 데이터 저장 단위로 Transaction을 분리하여 rollback이 다른 Transaction에 전파되지 않도록 변경
- 반복문을 돌며 데이터를 조회하던 구조에서 미리 전체 데이터를 조회한 뒤 이를 Map에 저장하여 사용하도록 변경. DB 접근 횟수 n회 → 4회로 감소 (n: 라이더 수)
- 연결된 Entity는 fetchJoin을 사용, 그 외 Entity id로 조회하도록 쿼리를 분리해 Slow Query 속도를 1500ms로 개선
- runBlocking 내 async로 계산 및 데이터 입력 작업 병렬처리
- 데이터가 생기지 않았을 때 API를 한 번 더 실행하도록 이상탐지 Scheduler 개발

**[ 성과 ]**
- API 실행 속도 15분에서 10초로 개선

**Tech**: Kotlin, Spring Boot, JPA, Coroutine
